# 翻译规范

字幕翻译和文本翻译是两件事。字幕有它的物理约束——观众要用眼睛在一两秒内
扫完，还要顾着看画面——所以「准确」只是及格线，「好读」才是目标。

下面这套标准是拿真实项目（一场 3 分钟的英文产品发布会，52 句）打磨出来的。

---

## 一、术语必须统一

同一个产品名、同一个技术概念，全片只能有一种译法。前后不一致比翻错更伤——
观众会以为你在说两个不同的东西。

**动手前先建一张对照表**，遇到新术语随时往里加：

| 原文 | 译法 | 备注 |
|---|---|---|
| TypeSafe | TypeSafe | 产品名保留原文，不译 |
| Jev | Jev | 同上 |
| RLCD | RLCD | 缩写保留，首次出现时可加注 |
| reinforcement learning | 强化学习 | 固定译法 |
| token | token | 业界习惯，不译成"令牌" |

**专有名词的处理顺序**：
1. 先搜索核实正确拼写（识别环节经常听错）
2. 产品名/公司名/人名 → 保留原文
3. 通用技术术语 → 用业界通行译法，拿不准就用原文
4. 缩写 → 保留，必要时首次出现时展开

## 二、长度要收，但不硬凑

中文比英文紧凑，同样信息量通常只需要 60~70% 的字数。但这不是让你砍信息。

**判断标准**：读一遍，问自己「一秒钟看得完吗」。

- 一句话超过 **34 个汉字**（本项目 `wrap_zh` 的折行上限）就会折成两行，
  折行本身没问题，但如果原文一句话被撑到三行以上，观众跟不上。
- **该拆句就拆句**。英文的从句套从句，中文里硬压成一句会读不断气。
  拆的时候保持时间轴不动（一个 segment 内用逗号/句号分开即可）。
- **别把英文的语气词都译出来**。"Well", "You know", "So" 之类多数可以省掉，
  留着会让中文显得啰嗦。反过来，说话人明显的犹豫、强调、自嘲要保下来。

## 三、口语按口语翻

这是演讲、访谈、教程类内容最容易翻砸的地方。

- **不要书面语**。"这是非常重要的" → "这很关键"；"我们可以发现" → "你会发现"。
- **保持说话人的语气**。如果原文是在开玩笑，译出来也要像在开玩笑。
- **第一人称、第二人称跟着原文走**，不要为了"客观"改成"我们"。
- **数字、单位、专有符号原样保留**：`$42/十亿 token`、`6.83 Mbps`、`4K` 别译。

反面例子：

| 原文 | 差译 | 好译 |
|---|---|---|
| Let's get started. | 让我们开始吧。 | 那我们开始。 |
| It works really well. | 它工作得非常好。 | 效果确实很好。 |
| We're going to show you… | 我们将会向您展示…… | 我们接下来看…… |

## 四、不逐字直译

英文的语序、被动、虚词在中文里照搬就会变成翻译腔。

- **被动改主动**：`The model was trained on…` → `模型训练用的是…`，不是「模型被训练在…」
- **名词化改动词化**：`the implementation of the feature` → `实现这个功能`，
  不是「该功能的实现」
- **长定语拆开**：英文喜欢把定语堆在名词前，中文要拆成短句

## 五、翻完之后

1. **读一遍**。对着 `segments.json` 的原文，从头到尾扫一次译文，
   专挑拗口的地方改——读不顺的句子观众也读不顺。
2. **跑校验**：
   ```bash
   <PY> scripts/check_translations.py <工作目录>
   ```
   它会抓出条数错位、空译、明显漏翻（译文与原文完全相同）、异常长句。
3. **抽查对齐**。挑开头、中间、结尾各一句，对一下时间轴和内容是否匹配。
   一旦发现整体错位一格，说明翻译顺序出问题了，必须重来。

---

## 给 AI 助手的操作要点

- **先通读再动笔**。不要拿到第一句就开始翻——整段内容看完，术语和语气
  才能定下来。
- **长视频分批**，但每批都带上「前文摘要」和「术语表」，保证跨批次一致。
- **写 translations.json 时严格保持顺序和条数**。这是整条流水线唯一会
  静默出错的地方，写完立刻跑校验脚本。
- **不确定的专有名词先查再写**，不要猜。猜错的代价是它会在译文里
  被反复强化。
